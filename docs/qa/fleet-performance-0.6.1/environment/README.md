# Fleet display setup and excluded preflight attempts

All three paired comparisons use private Sway 1.12 GPU displays with the same [configuration](sway-headless.conf): one 1600×1000 output at 60 Hz and scale 1, with floating, borderless 1440×900 native windows. These are separate compositor processes and sockets; the user's desktop, system packages and power settings were not changed. The original September 27 user-desktop table remains a separate historical comparison.

[Display provenance](display-provenance.json) records the executable/configuration hashes, output geometry and GLES renderer: Apple M1 Pro, AMD Radeon Graphics and Intel Iris Plus Graphics 645. The x86 hosts use identical Sway, wlroots and libliftoff package archives extracted into task-local directories. Their signatures were verified against each host's installed Arch Linux keyring. The private library path applies only to the compositor; benchmark applications use their ordinary host libraries and the pinned ONNX Runtime library. The runner rejects inherited library overrides.

The native application receipts also check actual open hardware render-node descriptors. Most kernels expose the driver through `/proc/<pid>/fdinfo`. This Asahi kernel does not; its collector resolves the actual open character-device descriptor through `/sys/dev/char/<major>:<minor>/device/driver` and records that evidence source. Open descriptors and compositor renderer identity are hardware-backend evidence, not GPU frame-time measurements. The final x86 [fdinfo collector](../runner-versions/run_paired-fdinfo.py) and [Asahi-compatible collector](../run_paired.py) have identical Python syntax trees outside `gpu_handles`; the report validates their exact source hashes and this boundary.

[Excluded attempts](excluded-attempts.json) preserve identities, exit statuses, assertion results and validation errors from these earlier attempts. None contributes timing samples to the final report:

- HP and Intel first stopped because the runner assumed a 1020×771 candidate canvas. The actual saved end-state was 1014.71875×771 on both machines, subsequently confirmed on M1. The inspector has a default width and a content-dependent minimum; current character controls differ from the original issue-158 application. The expected end-state width was corrected exactly before fresh complete runs. Native 1440×900 windows, 1200×900 exports, action counts and functional assertions remained strict.
- M1 first stopped because the fdinfo-only collector found no `drm-driver` fields. Its baseline authoring process exited successfully, preserved the expected canvas geometry and passed its native assertions. The collector was corrected to identify the actual open Asahi device through sysfs, then a fresh complete matrix was launched.

The canvas rectangle is reported at the end of authoring. This does not prove that every earlier phase had that final geometry: panels can expand during editing, and fitting occurs at startup and completion. The report preserves the actual per-run rectangle and compares exported document pixels separately. Raw failed receipts remain unchanged; their failure statuses describe instrumentation assumptions rather than failed product assertions.
